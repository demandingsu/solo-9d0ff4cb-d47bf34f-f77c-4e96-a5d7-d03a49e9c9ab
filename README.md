# 灯杆故障单入仓核对系统（Flask + SQLite）

巡检台账与维修台账把**两根灯杆误认成同一根**时，故障单会挂到多个资产号上。
本系统用网页完成入仓核对：上传资产号清单、故障单与同杆确认，按同杆关系把灯杆并成
冲突组，给出“撤销一条同杆确认即可让组内每张单都有唯一资产号”的方案；选定后按
**撤销提交时生效的整版资产清单**复算，条件满足才撤销并生成整组入仓清单。

## 一、启动（Docker Compose）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

SQLite 数据文件落在宿主机 `./data/recon.db`（compose 已挂载卷），重建容器不丢数据。
停止：`docker compose down`。

## 二、CSV 格式（均为 UTF-8，首行表头）

| 上传类型 | 列 | 说明 |
|---|---|---|
| 资产号清单 | `asset_no,pole_source,pole_no` | 资产号全局唯一；**整版换表，已有入仓记录也允许上传**。新版缺失的号停用（行保留），同号可改挂另一根灯杆 |
| 故障单 | `ticket_no,source,pole_source,pole_no` | 单号按来源台账区分；可补传，同 `(source,ticket_no)` 为更新；已核对单不能改挂灯杆 |
| 同杆确认 | `source_a,pole_no_a,source_b,pole_no_b[,confirmed_by]` | 被认成同一根的两根灯杆引用；可补传，幂等；撤销后同对灯杆可再次确认 |

样例见 `sample_data/`（`assets_v2.csv` 是换表演示样例：停用 `AST-001`、`AST-002/003`
改挂、新增 `AST-004/005`）。编号在页面统一显示为 `来源/编号`，从根上区分不同台账的同号灯杆/单号。

## 三、整版换表规则（本次新增的核心能力）

资料员可在网页直接上传整份资产 CSV 换表，**即使故障单已核对、已入仓也不拒绝**：

1. **新版没有的资产号 → 停用（`asset.active=0`），不删行**。历史 `verified`/入仓清单
   外键与回查全部保留，入仓页照旧显示原资产号并标注“已停用”。
2. **同一资产号改挂另一根灯杆 → 更新灯杆引用，资产 id 不变**。已核对单仍锁定原号，
   入仓页标注“已改挂（现挂 …，入仓归属不变）”。
3. **新版新出现的号 → 插入**；曾停用的号重新出现 → 重新启用并按新版挂杆。
4. 每次成功换表生成一版 `asset_version`；撤销方案与入仓清单都记下提交时生效的版本号。
5. **换表失败继续用旧表**：文件解析错误（空文件、缺列、号重复）或事务写入失败时，
   不生成新版本、不动任何旧数据，页面明确提示。

### 占号与候选池（组详情与撤销复算同一套规则）

- **已核对单沿用原资产号，并在所在组内占住这个号**——即使该号已停用或已改挂到别的
  灯杆，组内其他单（含待核对单）都不能再用；
- **待核对单只能用新版清单里、挂在本组灯杆上、且未被占住的活动资产号（同组空余）**；
- 已核对单的归属由它所挂的灯杆带入当前连通组；换表与撤销交错时，`apply_plan`
  每次重新加载当前快照，**天然按撤销提交那一刻生效的整版清单判定**；
- 若已无解（任意单条撤销都无法让每张单拿到唯一号），页面提示**重选**，不撤销任何确认、
  不改原关系与入仓记录。

## 四、核对与撤销规则（实现要点）

1. **按来源区分编号**：灯杆、故障单都以 `(来源, 台账内编号)` 为自然主键，不同台账同号互不覆盖。
2. **同杆确认可传递**：活动确认构成无向图，并查集求连通组；一张确认撤销后只影响它所在的组。
3. **冲突组**：含 ≥2 个灯杆引用且有故障单的连通组。组内活动资产为各灯杆活动资产并集，
   再并入已核对单锁定的号；每张故障单必须匹配不同资产号（二分图 Kuhn 匹配，确定性结果）。
4. **单条撤销方案**：逐条模拟“移除该确认”，当且仅当拆出的每个子组都能一一匹配时列为方案，
   页面同时给出撤销后每张单的归属资产号及资产状态（活动/已移走/已停用）；没有可行方案时提示**无解**。
5. **选定方案后按提交时生效的整版清单复算**（不依赖选方案时的快照）：
   - 重新定位组、确认该确认仍活动且仍在组内（资料已变则要求**重新选择**）；
   - 模拟撤销重新匹配；
   - **已核对单子归属不变（停用/移走也照样占号）**、且最新组里的新单也都有同组空余号唯一归属，
     两个条件同时满足才执行；
   - 撤销确认、锁定归属、生成整组入仓清单在**单个 SQLite 事务**内完成，并写入当前资产版本号；
   - 条件不符或写入失败一律回滚，保留原关系和归属并提示原因。

## 五、页面

- `/` 上传三种 CSV；展示活动/停用资产数、当前生效资产清单版本、数据统计、冲突组
  （当前是否可唯一归属、已选方案、入仓链接）、上传批次。
- `/groups/<key>` 组详情：故障单/候选资产/**资产号状态表（空余可分配、已核对单占号、
  已停用、已改挂别杆）**/已核对锁定单；列出全部单条撤销方案及撤销后归属；无解提示。
- `/warehouse/<id>` 整组入仓清单：每张单的唯一资产号、资产当前状态（活动仍挂原杆/
  已改挂/已停用）、核对状态，并标注清单依据的资产清单版本。

## 六、旧库升级

旧版本数据库启动时自动迁移（`app/db.py::_migrate`）：补 `asset.active/version_id`、
`undo_plan/warehouse.asset_version_id` 列，新建 `asset_version` 表，并把库内现有资产
清单登记为**第 1 版（旧库升级：沿用库内现有资产清单）**，已有入仓记录回填该版本号、
回查原资产号不变；迁移后即可在旧库上直接换表。

## 七、验证

自动化测试（16 个用例，Flask test client + 临时 SQLite）：

```bash
python tests/test_recon.py
```

1–9 为基线用例（三类上传与补传/幂等、来源编号区分、传递分组、方案选择与撤销入仓、
补传后仍可撤销、补传后无解与须重选、坏 CSV 整体拒收、写入失败事务回滚）。
10–15b 为换表专项：

- `test_10` 换表停用/改挂/新增，旧入仓记录照旧回查原号、版本登记；
- `test_11` **移号后新旧单混组**：停用/移走号被已核对单占住，待核对单只用同组空余号；
- `test_12` 待核对单无同组空余号 → 无解提示重选，原关系与入仓记录保留；
- `test_13` **换表与撤销交错**：同一撤销在不同版本下可行/无解/恢复可行，按提交版本判定；
- `test_14` 坏文件/空文件换表整体拒收，继续用旧表；
- `test_15` 旧库结构自动迁移、现有清单登记第 1 版、迁移后可继续换表；
- `test_15b` **跨组占号**：已核对单的号改挂到别的组后，该组待核对单仍不可使用。

## 九、余项与边界

- 资产号以“资产号全局唯一”为业务键；换表只停用不删行，停用号重新出现即复用原行。
- 已核对故障单不允许改挂灯杆（其归属与所在组由灯杆位置决定），待核对单可正常补传更新。
- 单机部署、SQLite 单文件；如需多实例，可换 PostgreSQL（DAO 集中在 `db.py`/`services.py`）。
- 未做登录鉴权，内网工具定位；上生产前需加认证并替换 `app.secret_key`。
- 冲突组只展示由同杆确认合并出来的多灯杆组；单灯杆自身“单多于资产”的资料问题不在本流程处理范围。
